# HEMS Survivor MVP v0.1 完整设计规格

## 1. 文档目的与优先级

本文档冻结 HEMS Survivor MVP v0.1 的产品规则、技术架构、基准数值、界面范围和验证方式，使开发可以在没有额外产品猜测的情况下开始。

当现有资料对 MVP 规则描述不一致时，按以下优先级执行：

1. 本设计规格。
2. `MVP_V0.1.md` 的范围与验收要求。
3. `MVP_V0.1_PLAN.md` 的阶段和依赖关系。
4. `GAME_DESIGN.md` 的长期方向。
5. `ROADMAP.md` 的后续阶段设想。

本文所有数值都是第一版可调试基线。试玩可以调整配置值，但规则含义和系统边界的改变必须先更新本文档。

## 2. 产品目标

在手机浏览器中提供一个可完整开始、暂停、继续、胜利或失败并重开的单屏 Roguelike 能源调度小游戏。

目标体验：

- 新玩家在 30 秒内理解 Home 供电目标和主要控制。
- 标准对局持续 6 分钟。
- 第 5～6 分钟为最终电网危机，撑到 6 分钟即胜利。
- Battery、EV 和 Grid 的操作可以改变至少一次危险局面。
- 三次升级选择能够形成可描述的策略差异。
- 每次失败都能说明主要原因和关键时间点。

## 3. MVP 范围

### 3.1 必须包含

- 开始、暂停、继续、胜利、Game Over 和重开。
- 一秒一次的确定性 Tick。
- Solar、Home、Battery、EV、Grid 五类能源对象。
- Money、Family、Score 三项资源。
- Battery 充电/自动/放电三种模式。
- EV 暂停/充电两种模式。
- Grid 买电和卖电开关。
- 阴天、高峰电价、家庭负载上升、EV 紧急出行四类事件。
- 90、180、270 秒的三次升级三选一。
- 六个可选升级和固定随机种子。
- 当前能源流向、风险提示、事件反馈、结局摘要。
- 以 360×800 为最低基准的竖屏响应式界面。

### 3.2 明确不包含

- 后端、账号、联网玩法、排行榜、云存档和多人模式。
- 局外成长、每日任务、付费、商店和成就系统。
- EV 放电、V2H 和真实电网物理模拟。
- 多地图、多角色、大型内容库和复杂叙事。
- 重型游戏引擎、复杂状态管理框架和高成本动画音频。
- 对局中途存档；刷新页面等同开启新局。

## 4. 技术架构

### 4.1 技术栈

- React。
- TypeScript。
- Vite。
- Vitest。
- React Testing Library。
- Playwright。
- CSS Modules 或普通模块化 CSS；不引入组件库。

### 4.2 系统边界

```text
React UI
   ↓ PlayerAction
Game Controller
   ↓ Action / Tick
Pure TypeScript Game Engine
   ↓ GameState + TickReport
React UI rerender
```

模块职责：

- `game/config`：保存所有可调数值和测试用加速配置。
- `game/types`：定义状态、操作、事件、升级和报告类型。
- `game/state`：创建初始状态和新局。
- `game/random`：提供可序列化、可复现的种子随机数。
- `game/energy`：结算 Solar、Home、Battery、EV、Grid。
- `game/events`：事件预警、触发、持续、结束和结果。
- `game/upgrades`：候选抽取与升级应用。
- `game/scoring`：Money、Family、Score 与胜负判断。
- `game/engine`：按固定顺序执行单个 Tick，并产生结算报告。
- `game/controller`：管理计时器、暂停、操作和页面生命周期。
- `ui`：只展示状态并发送意图，不直接修改底层资源。

规则层不得导入 React、浏览器 API 或 UI 文件。相同配置、初始状态、随机种子和操作序列必须得到相同结果。

## 5. 时间与对局状态

### 5.1 时间规则

- 一个逻辑 Tick 等于一秒游戏时间。
- 标准对局共 360 个 Tick。
- MVP 不提供倍速按钮。
- 暂停、升级选择、页面后台、胜利和失败期间不推进 Tick。
- 恢复页面后必须由玩家主动继续，不补算后台时间。

### 5.2 状态机

```text
ready → running ↔ paused
          ↓
     choosingUpgrade
          ↓
       running
          ↓
     victory | gameOver
          ↓
         ready
```

- `ready`：显示开始说明，计时器未启动。
- `running`：每秒只允许执行一次 Tick。
- `paused`：保留当前状态，不执行 Tick。
- `choosingUpgrade`：显示三选一并暂停所有倒计时。
- `victory` / `gameOver`：只触发一次并永久停止本局计时器。
- 重开创建全新的初始状态、种子、事件队列和计时器。

## 6. 初始状态与通用边界

MVP 使用抽象“电量单位”，不声称对应真实 kWh。

| 项目 | 初始值 | 边界或功率限制 |
|---|---:|---:|
| Battery 电量 | 60 | 0～100 |
| Battery 充电功率 | 1.0/秒 | 不得超过剩余容量 |
| Battery 放电功率 | 1.0/秒 | 不得超过当前电量 |
| EV 电量 | 30 | 0～80 |
| EV 充电功率 | 0.6/秒 | 不得超过剩余容量 |
| Money | 120 | 最低 0，不设硬上限 |
| Family | 100 | 0～100 |
| Score | 0 | 最低 0，不设硬上限 |
| Grid 买电功率 | 0 | 最大 2.0/秒 |
| Grid 卖电功率 | 0 | 最大 1.0/秒 |

默认操作状态：

- Battery：自动。
- EV：暂停。
- Grid：允许买电，禁止卖电。
- Battery 自动储备线：25。

规则计算保留完整小数精度，界面统一显示一位小数。浮点误差绝对值小于 `0.000001` 时视为 0。

## 7. Solar、Home 与阶段曲线

| 游戏时间 | 阶段 | Solar 基准 | Home 基础负载 |
|---|---|---:|---:|
| 0～59 秒 | 安全期 | 1.4 | 1.0 |
| 60～179 秒 | 学习期 | 1.2 | 1.1 |
| 180～299 秒 | 压力期 | 0.9 | 1.2 |
| 300～359 秒 | 电网危机 | 0.5 | 1.4 |

每 Tick 使用固定种子分别生成：

- Solar 波动系数：闭区间 `[0.9, 1.1]`。
- Home 波动增量：闭区间 `[-0.1, 0.1]`。

计算顺序：

```text
solarOutput = solarBase × randomSolarFactor × eventModifier × upgradeModifier
homeLoad = max(0, (homeBase + randomHomeDelta + eventDelta) × upgradeModifier)
```

界面必须显示本 Tick 的实际 Solar 和 Home 值。随机波动不改变事件或升级文字中声明的倍率。

## 8. 能源结算

### 8.1 每 Tick 固定顺序

1. 读取阶段基准、事件、升级、价格和控制模式。
2. 计算实际 Solar 和 Home。
3. Solar 优先供给 Home。
4. Home 仍有缺口时，根据 Battery 模式放电。
5. Home 仍有缺口且允许买电时，从 Grid 买电。
6. 记录仍未满足的 Home 负载和连续断电时间。
7. Solar 有余量时，根据 Battery 模式为 Battery 充电。
8. Battery 为充电模式且 Solar 不足、允许买电时，从 Grid 为 Battery 充电。
9. EV 为充电模式时，依次使用 Solar 余量、Battery 放电模式的剩余放电功率、Grid 买电。
10. 允许卖电时，先出售最后的 Solar 余量，再使用 Battery 放电模式的剩余放电功率；两者合计不得超过 Grid 卖电功率上限。
11. 不能使用或出售的能量记为弃电。
12. 结算 Money、Family、Score、事件、升级节点和胜负。

每个 Tick 必须返回各来源到各目标的精确流量。所有流入之和必须等于已使用、存储、出售、短缺和弃电之和。

### 8.2 Battery 模式

**充电**

- 不主动放电。
- 使用 Solar 余量充电。
- Solar 不足且 Grid 允许买电时，可在 Grid 买电功率余量内充电。
- Battery 满电后停止请求能源。

**自动**

- Solar 有余量时充电。
- Home 缺电时放电，但不得让 Battery 低于 25。
- 不主动从 Grid 充电。
- 不为 EV 放电，也不主动向 Grid 卖电。

**放电**

- 在功率和当前电量范围内优先支援 Home。
- 剩余放电功率可以支援正在充电的 EV。
- 仍有剩余功率且允许卖电时，可以向 Grid 卖电。
- 不设置自动储备线；玩家承担放空 Battery 的风险。

Battery MVP 充放电效率为 100%，不产生隐藏损耗。

### 8.3 EV 模式

**暂停**

- 不请求电量。

**充电**

- Home 完成供电后，每 Tick 请求最多 0.6 电量。
- 来源依次为 Solar 余量、Battery 放电模式的剩余功率、Grid。
- EV 满电后停止请求。
- EV 不得放电或卖电。

### 8.4 Grid 与 Money

- 基础买价：`1.0 Money/电量`。
- 基础卖价：`0.6 Money/电量`。
- Grid 买电和卖电是两个独立开关。
- 即使两个开关都开启，同一 Tick 也不得同时买入和卖出。
- 发生买电后，本 Tick 的所有卖电流量为 0。
- Money 不足时只购买实际可支付的电量。
- `buyCost = boughtEnergy × effectiveBuyPrice`。
- `sellIncome = soldEnergy × effectiveSellPrice`。
- Money 最低为 0；Money 为 0 不直接导致 Game Over。

## 9. Family、断电与胜负

### 9.1 Family

- Home 存在任何未满足负载的 Tick：Family `-2`。
- Home 完全满足的 Tick：连续稳定计时加 1。
- 连续稳定 30 个 Tick：Family `+1`，随后稳定计时归零。
- 再次断电时稳定计时立即归零。
- 事件奖励或惩罚应用后将 Family 限制在 0～100。

### 9.2 Game Over

满足任一条件立即失败：

- Family 等于 0，主要原因记为“家庭满意度耗尽”。
- Home 连续 10 个 Tick 存在未满足负载，主要原因记为“持续断电”。

如果两者在同一 Tick 同时发生，优先记录“持续断电”，并在摘要中同时显示 Family 已归零。

EV 事件失败和 Money 为 0 均不会直接结束对局。

### 9.3 胜利

- 游戏时间达到 360 秒且本 Tick 未先触发 Game Over 时胜利。
- 胜利只触发一次，并立即停止 Tick。
- 胜利奖励 Score `+500`。

## 10. 事件系统

### 10.1 生命周期与调度

事件状态按以下顺序变化：

```text
scheduled → warning → active → resolved → cooldown
```

- 普通事件同时最多存在一个。
- 55 秒进入第一项事件预警，60 秒开始第一项事件。
- 事件结束后，根据当前阶段使用固定种子生成下一段冷却：
  - 学习期：45～60 秒。
  - 压力期：35～50 秒。
- 冷却结束后先进入该事件自己的预警阶段，再激活事件。
- 不允许连续两次抽到相同事件。
- 如果新事件完整活动窗口会越过 300 秒，则取消该次调度。
- 300 秒开始电网危机时不得存在普通事件。
- 暂停和升级选择期间，预警、活动和冷却均停止计时。

### 10.2 阴天

- 预警：5 秒。
- 活动：25 秒。
- 效果：Solar 输出乘以 `0.4`。
- 结束：移除倍率，生成“光伏输出恢复”报告。
- 无独立成功奖励；玩家通过 Battery 或 Grid 维持 Home。

### 10.3 高峰电价

- 预警：10 秒。
- 活动：30 秒。
- 买价变为 `2.2`。
- 卖价变为 `1.4`。
- 电网合约升级在事件价格基础上继续应用。
- 结束：价格恢复基础值，生成价格恢复报告。

### 10.4 家庭负载上升

- 预警：5 秒。
- 活动：25 秒。
- Home 在阶段基准和随机波动之后额外增加 `0.6`。
- 活动期间 Home 每 Tick 都完全满足：结束时 Family `+5`、Score `+100`。
- 任一活动 Tick 出现短缺：事件正常结束，但无奖励；断电的常规 Family 惩罚仍然生效。

### 10.5 EV 紧急出行

- 预警：5 秒。
- 活动：45 秒。
- 激活时目标为 `min(EV 容量, 当前 EV 电量 + 15)`。
- 截止 Tick 结算后 EV 达到目标：Score `+150`。
- 未达到目标：Family `-15`、Score `-100`，Score 最低为 0。
- 提前达到目标时事件仍显示“已满足”，并在原截止时间结算成功；玩家可暂停 EV 充电。

### 10.6 最终电网危机

- 300～359 秒持续生效。
- 使用危机阶段的 Solar 和 Home 基准。
- Grid 从 300 秒起按“开放 10 Tick、关闭 10 Tick”循环。
- 关闭期间禁止所有买电和卖电，并显示重新开放倒计时。
- 危机期间不生成普通事件。
- 到达 360 秒且未失败即完成危机并胜利。

## 11. 升级系统

### 11.1 触发与抽取

- 在游戏时间首次达到 90、180、270 秒时触发。
- 触发后状态进入 `choosingUpgrade`，所有计时停止。
- 从当前未选择的升级中使用固定种子无重复抽取 3 个候选。
- 已选择升级永久移出本局候选池。
- 当次未选择升级保留，后续可以再次出现。
- 每次只能确认一个升级；重复点击不得重复应用。

### 11.2 六个升级

| ID | 名称 | 精确效果 |
|---|---|---|
| `battery_capacity` | 扩容电芯 | Battery 容量 +25，当前电量 +10，当前电量不超过新容量 |
| `battery_power` | 高功率逆变器 | Battery 最大充电和放电功率各 +0.35 |
| `solar_optimizer` | 光伏优化 | Solar 最终输出永久乘以 1.25 |
| `home_efficiency` | 家庭节能 | Home 最终负载永久乘以 0.85 |
| `ev_fast_charge` | EV 快充 | EV 最大充电功率 +0.25 |
| `grid_contract` | 电网合约 | 有效买价乘以 0.85，有效卖价乘以 1.15 |

MVP 每项升级只能选择一次，不存在等级、稀有度或隐藏副作用。

## 12. Score

每 Tick 和事件结算按以下规则改变 Score：

- 完成一个存活 Tick：`+1`。
- 本 Tick Solar 直接供给 Home 或 EV 的每 1 电量：`+2`。
- Solar 充入 Battery 后再次使用不重复计算 Solar 分数。
- 家庭负载上升事件成功：`+100`。
- EV 紧急出行成功：`+150`。
- EV 紧急出行失败：`-100`，最低为 0。
- 完成电网危机：`+500`。

Score 计算保留小数，界面显示四舍五入后的整数。结局页单独显示 Money 和 Family，不将二者再次折算进 Score。

## 13. 随机数与可复现性

- 使用纯 TypeScript 的确定性伪随机数生成器。
- 新局默认用当前时间生成种子并在结局页显示。
- 地址参数 `?seed=<unsigned-integer>` 可指定调试种子。
- 非法或缺失种子使用当前时间生成，并规范化为无符号整数。
- Solar 波动、Home 波动、事件冷却、事件类型和升级候选共用同一可序列化随机状态，但通过固定调用顺序保证复现。
- 测试必须证明相同种子和操作序列产生相同关键状态与报告。

## 14. Tick 报告与可解释性

每个 Tick 返回 `TickReport`，至少包含：

- Tick 编号和阶段。
- 实际 Solar、Home 和 Grid 价格。
- 每条能源流向的来源、目标和电量。
- Home 未满足负载和连续断电时间。
- Money、Family、Score 的变化量与原因代码。
- 事件预警、开始、成功、失败和结束记录。
- 升级节点、胜利或 Game Over 记录。
- 弃电量。

UI 根据结构化原因代码生成中文提示。结局摘要保留本局最近的关键记录，不解析自由文本来判断原因。

## 15. 界面设计

### 15.1 布局

以 360×800 竖屏为最低设计基准，自上而下排列：

1. 顶部状态栏：时间、Money、Family、Score、暂停按钮。
2. 能源总览区：Solar、Home、Battery、EV、Grid 状态卡与能源流向。
3. 事件与风险区：当前事件、倒计时、连续断电和最大风险。
4. 操作区：Battery 三段选择、EV 两段选择、Grid 两个开关。
5. 弹层：开始、升级、暂停、胜利和 Game Over。

手机横屏和桌面浏览器可以运行，但 MVP 不为其制作独立复杂布局。

### 15.2 交互与可访问性

- 主要按钮点击区域至少 44×44 CSS 像素。
- 当前模式同时使用文字、形状或图标和颜色表达。
- 警告不得只依赖红绿颜色。
- 不可用按钮必须显示原因，例如“余额不足”或“电网关闭”。
- 首次开始页只显示三条说明：保证 Home、使用 Battery、根据事件控制 EV/Grid。
- 能源状态和玩家操作必须在下一个 Tick 内产生可读反馈。

## 16. 防错与恢复

- 所有状态变化只能来自 Action、升级应用或单次 Tick。
- 每 Tick 后校验数值有限、容量不越界、资源不低于下限。
- 开发环境遇到非法配置或状态时立即抛出带原因的错误。
- 正式界面遇到不可恢复错误时暂停游戏，显示错误提示和重开按钮。
- 使用逻辑 Tick，不根据渲染帧数结算。
- 页面进入后台自动暂停；返回后不补算时间。
- 连续点击开始、暂停、升级或重开不得创建重复计时器。
- 胜利或 Game Over 后所有事件、升级和 Tick 停止。

## 17. 测试与验收

### 17.1 规则单元测试

- 五类能源对象的基本结算和能量守恒。
- Battery 三种模式、功率限制和自动储备线。
- EV 来源优先级、功率和容量边界。
- Grid 买卖互斥、余额不足、基础价格和高峰价格。
- Family 恢复、Family 归零、连续断电和胜负优先级。
- 四类事件的预警、触发、持续、结束和结果。
- 六个升级的精确效果、候选去重和单次应用。
- 固定随机种子的 Solar、Home、事件和升级复现。
- 暂停、升级选择、后台和结局期间不推进 Tick。
- 360 秒胜利与 300～359 秒电网开关周期。

### 17.2 React 集成测试

- 开始、暂停、继续、升级选择、胜利、Game Over 和重开。
- UI 发送 Action，不直接修改规则状态。
- 状态卡、能源流向、事件、风险和升级效果展示。
- 连续重开三局不存在旧状态或重复计时器。
- 错误边界显示可恢复提示。

### 17.3 浏览器验收

- Playwright 使用 360×800 和 390×844 两种视口。
- 页面无横向滚动，核心按钮可见且可点击。
- 使用测试配置加速完成一次胜利、Family 归零失败和持续断电失败。
- 正式构建可以在同一网络的真实手机浏览器打开并完成至少一局。

### 17.4 MVP 完成定义

只有以下条件全部满足才算完成：

- `MVP_V0.1.md` 的全部必须项均有实现证据。
- 单元、集成和浏览器测试全部通过。
- 同一页面可以连续完成并重开三局。
- 标准配置下普通一局在 360 秒进入胜利或此前合理失败。
- 新玩家能在 30 秒内指出主要资源、危险和操作目标。
- 玩家操作至少改变一次危险局面的结果。
- 至少两种升级组合产生可描述的策略差异。
- Game Over 摘要明确显示主要原因、关键时间点和升级列表。
- 未实现本规格明确排除的系统。
