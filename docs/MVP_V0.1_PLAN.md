# HEMS Survivor MVP v0.1 执行计划

## 1. 计划目标

在手机浏览器中交付一个可以完整开始、游玩、胜利或失败并重开的单屏网页小游戏，用最小范围验证以下核心循环是否成立：

```text
观察能源供需
    ↓
调整 Battery / EV / Grid 策略
    ↓
处理事件与资源压力
    ↓
选择 Roguelike 升级
    ↓
应对阶段性高压事件
    ↓
复盘结果并重开
```

本计划不估算人力和工期。任务按依赖关系推进，前一阶段未达到出口标准时，不进入下一阶段。

## 2. 范围基线

### 必须交付

- 手机浏览器单屏游戏界面。
- 开始、暂停、继续、胜利、Game Over 和重开流程。
- Solar、Home、Battery、EV、Grid 五类能源对象。
- Money、Family、Score 三项玩家资源。
- Battery 三种模式、EV 两种模式和 Grid 买卖开关。
- 阴天、高峰电价、家庭负载上升、EV 紧急出行四类事件。
- 至少 6 个升级；一局至少出现 3 次三选一。
- 约 5～8 分钟的完整对局和一个阶段性高压事件。
- 可读的能源流向、风险提示、升级反馈和对局总结。

### 暂不交付

- 账号、联网、排行榜、云存档和多人模式。
- 局外成长、每日任务、付费、商店和成就系统。
- EV 放电、V2H 和复杂真实电网模拟。
- 多地图、多角色、大型内容库和商店级美术。
- 高成本动画、完整音频包及原生 App 能力。

## 3. 推进路线

采用“规则优先 + 试玩切片”的方式：先冻结可计算、可测试的规则，再做 2 分钟可玩切片，随后补齐完整内容并扩展至 5～8 分钟。

| 阶段 | 主要产出 | 前置依赖 | 阶段出口 |
|---|---|---|---|
| 0. 规则冻结 | 数值表、结算顺序、事件与胜负规则 | 已有策划文档 | 可以不用代码推演一局关键节点 |
| 1. 规则内核 | 确定性 Tick、能源与资源结算 | 阶段 0 | 固定输入能稳定得到固定结果 |
| 2. 两分钟切片 | 最小单屏 UI 与短局流程 | 阶段 1 | 手机浏览器可独立玩完短局 |
| 3. 事件与升级 | 4 类事件、6 个升级、三选一 | 阶段 2 | 操作和 Build 能明显改变局势 |
| 4. 完整对局 | 5～8 分钟曲线、高压事件、结局 | 阶段 3 | 可完整胜利或 Game Over 并重开 |
| 5. 移动端与反馈 | 窄屏适配、提示、复盘摘要 | 阶段 4 | 新玩家可理解、操作和复盘 |
| 6. MVP 验收 | 连续试玩、边界测试、数值调整 | 阶段 5 | 满足 MVP 全部验收条件 |

## 4. 详细计划表

### 阶段 0：冻结规则基线

| 编号 | 任务 | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|---|
| 0.1 | 确定一局的时间尺度 | Tick 频率、目标时长、升级节点、高压事件节点 | 无 | 能列出从 00:00 到胜利节点的完整时间线 |
| 0.2 | 确定初始状态与边界 | Solar、Home、Battery、EV、Money、Family 初始值及上下限 | 0.1 | 所有可变化数值都有初值、单位和合法范围 |
| 0.3 | 定义能源结算顺序 | 每 Tick 能源流向和优先级规则 | 0.2 | 同一状态只有一种明确结算结果；Home 始终优先 |
| 0.4 | 定义玩家控制规则 | Battery、EV、Grid 各模式行为和切换限制 | 0.3 | 每个按钮都能说明即时效果、代价和不可用条件 |
| 0.5 | 定义资源与胜负规则 | Money、Family、Score 变化公式及结局条件 | 0.3 | 胜利与每种 Game Over 都可通过具体状态触发 |
| 0.6 | 定义事件与升级数据 | 4 类事件和至少 6 个升级的参数表 | 0.4、0.5 | 每项包含触发、持续、效果、反馈和结束规则 |
| 0.7 | 手工推演三条典型路径 | 稳定供电、主动卖电、错误操作三份推演记录 | 0.1～0.6 | 三条路径均无歧义、无负数、无无法解释的突变 |

阶段决策基线：

- MVP 不支持 EV 放电或向 Grid 卖电。
- Home 供电优先于 Battery 充电和 EV 充电。
- Grid 同一 Tick 不允许同时买电和卖电。
- 首个阶段性高压事件安排在完整对局约 5～8 分钟内。
- Money 不直接承担重复的生存功能；如果采用负债失败，必须定义应急缓冲期。

### 阶段 1：建立可测试的规则内核

| 编号 | 任务 | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|---|
| 1.1 | 建立游戏状态模型 | 时间、能源对象、资源、模式和局面状态定义 | 阶段 0 | 任意时刻的完整局面可由单一状态描述 |
| 1.2 | 实现确定性 Tick | 单步推进与暂停保护机制 | 1.1 | 相同初始状态和输入序列产生相同结果 |
| 1.3 | 实现能源结算 | Solar、Home、Battery、EV、Grid 的分配逻辑 | 1.2 | 能量守恒；容量与功率不越界；流向可解释 |
| 1.4 | 实现资源结算 | Money、Family、Score 的变化与边界处理 | 1.3 | 所有变化都能追溯到明确原因，不出现非法值 |
| 1.5 | 实现对局状态机 | 准备、运行、暂停、胜利、失败和重开 | 1.2、1.4 | 暂停和结束后不再重复结算；重开恢复干净初态 |
| 1.6 | 建立固定随机种子 | 可复现的负载、天气和抽取接口 | 1.1 | 指定种子能重现同一局的关键随机结果 |
| 1.7 | 覆盖规则自动测试 | 正常、边界、冲突和结局测试集 | 1.2～1.6 | 规则基线中的关键路径全部通过自动测试 |

### 阶段 2：完成两分钟可玩切片

| 编号 | 任务 | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|---|
| 2.1 | 确定手机单屏信息层级 | 页面线框与状态优先级 | 阶段 1 | 首屏同时看见时间、资源、能源对象和主要控制 |
| 2.2 | 建立基础游戏页面 | 顶部状态、中部能源区、事件区和底部控制区 | 2.1 | 常见手机窄屏无需横向滚动，主要按钮易于点击 |
| 2.3 | 连接实时状态展示 | 数值、进度、价格、模式和能源流向 | 2.2、1.3 | 页面显示与规则状态保持一致，没有 UI 自行改数值 |
| 2.4 | 接入玩家操作 | Battery、EV、Grid 控制 | 2.3 | 每个操作在下一个 Tick 内产生可见、可解释的影响 |
| 2.5 | 接入短局流程 | 开始、暂停、继续、短局结局和重开 | 2.3、1.5 | 可连续完成 3 局，无需刷新网页 |
| 2.6 | 加入最小风险反馈 | 颜色、文字警告和关键变化提示 | 2.3 | 玩家能判断当前最危险的资源及变化原因 |

两分钟切片只验证能源调度和按钮反馈，不要求包含完整事件池、完整升级池或最终数值平衡。

### 阶段 3：补齐事件与 Roguelike 升级

| 编号 | 任务 | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|---|
| 3.1 | 建立事件生命周期 | 触发、提示、持续、结束和冷却机制 | 阶段 2、0.6 | 事件不会静默触发或在结束后继续生效 |
| 3.2 | 实现四类 MVP 事件 | 阴天、高峰电价、家庭负载上升、EV 紧急出行 | 3.1 | 每类事件均可重复触发，并至少有一种操作应对方式 |
| 3.3 | 建立升级抽取流程 | 暂停结算、三选一、确认和恢复游戏 | 阶段 2、1.6 | 选择时不推进 Tick；每次正好出现 3 个合法候选 |
| 3.4 | 实现至少六个升级 | 容量、效率、价格、事件或自动调度类效果 | 3.3 | 每个升级都能通过状态或结算差异被玩家感知 |
| 3.5 | 处理事件与升级组合 | 叠加顺序、上限、重复规则及冲突测试 | 3.2、3.4 | 组合不会造成非法状态、永久残留或无解局面 |
| 3.6 | 验证策略差异 | 防守、经济或储能等至少两种试玩路径 | 3.5 | 不同升级选择能带来可描述的玩法差异 |

### 阶段 4：扩展为完整对局

| 编号 | 任务 | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|---|
| 4.1 | 建立分段难度曲线 | 安全期、学习期、压力期和高压期参数 | 阶段 3 | 压力随时间增长，开局不会堆叠过多信息 |
| 4.2 | 安排升级节奏 | 一局至少 3 个升级节点 | 4.1、3.3 | 正常路径能遇到至少 3 次三选一，间隔足以感知效果 |
| 4.3 | 实现阶段性高压事件 | 首个 Boss 或等价规则压力 | 4.1、3.1 | 高压阶段改变规则或资源关系，不只是简单加大数值 |
| 4.4 | 完成胜利条件 | 目标时间或完成高压事件后的结算 | 4.3 | 满足条件只触发一次胜利，并停止继续结算 |
| 4.5 | 完成失败条件 | Family、断电容错及可选负债失败 | 4.1 | 每次失败都有唯一主要原因和关键时间点 |
| 4.6 | 完成结局与重开 | 胜利页、Game Over、本局摘要和重开 | 4.4、4.5 | 结局显示结果、关键资源、升级和主要成功/失败原因 |
| 4.7 | 校准单局长度 | 完整对局参数集 | 4.1～4.6 | 普通试玩可在约 5～8 分钟进入阶段性结局 |

### 阶段 5：移动端体验和信息反馈

| 编号 | 任务 | 交付物 | 依赖 | 验收标准 |
|---|---|---|---|---|
| 5.1 | 优化窄屏布局 | 目标手机宽度下的稳定单屏布局 | 阶段 4 | 主要信息不遮挡、不溢出，竖屏可完成全部操作 |
| 5.2 | 优化触控操作 | 足够大的点击区、禁用态和点击反馈 | 5.1 | 常用操作可单手完成，不易误触相邻控制 |
| 5.3 | 强化能源反馈 | 流向、短缺、充放电、买卖电的动态状态 | 5.1 | 玩家不用猜测当前电力从哪里来、到哪里去 |
| 5.4 | 强化风险提示 | 危险资源、事件倒计时和临界状态警告 | 5.3 | 事件不会在无提示下直接导致 Game Over |
| 5.5 | 强化升级反馈 | 选择前说明、选择后即时提示和持续效果展示 | 5.3 | 玩家能指出升级改变了哪个系统和当前收益 |

## 5. 关键依赖关系

```text
规则与数值冻结
    ├── 游戏状态模型
    ├── 确定性 Tick
    └── 固定随机种子
             ↓
能源与资源结算 ──→ 对局状态机
             ↓             ↓
        两分钟切片 ──→ 手机单屏交互
             ↓
      事件系统 + 升级系统
             ↓
     难度曲线 + 高压事件
             ↓
       完整结局与复盘
             ↓
      移动端验收与调优
```

禁止倒置的关键依赖：

- 未冻结结算规则前，不做正式数值平衡。
- 规则内核未通过测试前，不让 UI 直接修改资源。
- 两分钟切片不可玩前，不扩充事件和升级内容。
- 完整对局未闭环前，不投入高成本美术和动画。
- 失败原因不可解释时，不用继续加难度解决节奏问题。

## 6. MVP 总体验收清单

### 完整性

- [ ] 玩家可以开始、暂停、继续、胜利或 Game Over 并重开。
- [ ] Solar、Home、Battery、EV、Grid 均参与能源结算。
- [ ] Money、Family、Score 每 Tick 保持一致且有变化原因。
- [ ] 四类事件均能触发、持续、结束并被应对。
- [ ] 至少六个升级可被抽取和应用。
- [ ] 一局至少出现三次有效的三选一升级。
- [ ] 首个高压事件在目标时段内出现。

### 可理解性

- [ ] 新玩家在 30 秒内能说出主要状态和操作目标。
- [ ] 玩家能判断当前最危险的资源。
- [ ] 玩家理解 Battery 与 Grid 的基本用途。
- [ ] 能源流向、资源变化、事件效果和升级效果可读。
- [ ] Game Over 明确说明主要原因和关键时间点。

### 稳定性

- [ ] 同一随机种子可以复现同一局关键结果。
- [ ] 能量、容量、Money 和 Family 不出现非法越界。
- [ ] 暂停、后台、胜利和 Game Over 不会重复结算。
- [ ] 连续完成三局不需要刷新网页。
- [ ] 手机竖屏无横向滚动，核心按钮可可靠点击。

### 游戏性

- [ ] 玩家操作至少能挽回一次风险局面。
- [ ] 不同升级选择能产生至少两种可描述的策略路线。
- [ ] 事件有预警和应对窗口，不会随机瞬间杀死玩家。
- [ ] 普通一局约 5～8 分钟进入阶段性结局。
- [ ] 失败后玩家能提出下一局准备尝试的不同策略。

## 7. 需要在阶段 0 最终确认的产品决策

以下决策不会阻塞本计划建立，但必须在规则实现前冻结：

1. Tick 对应的游戏时间以及是否允许加速。
2. Battery 充放电功率、效率和自动模式策略。
3. EV 紧急出行的目标电量、截止时间和失败后果。
4. Grid 的基础价格、波动方式及买卖价差。
5. Family 在断电、高价用电和事件中的变化公式。
6. Money 是否允许负数，以及负债是否构成 Game Over。
7. Score 只用于总结，还是会影响局内升级节点。
8. 阶段性高压事件的具体规则和胜利触发方式。

## 8. 完成定义

只有当以下条件同时满足时，MVP v0.1 才算完成：

- `MVP_V0.1.md` 的全部必须项已经实现。
- 规则、边界、事件、升级和状态机已有自动化验证。
- 手机浏览器中可以连续完成至少三局。
- 新玩家能理解主要操作、危险来源和失败原因。
- 对局能够体现至少两种策略差异，并让玩家操作改变结果。
- 未引入暂不包含的系统，也没有用复杂内容掩盖核心循环问题。
