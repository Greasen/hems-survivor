# Codex 后续实现说明

本文档用于后续把策划需求交给 Codex 实现时，统一范围、顺序和质量标准。

## 1. 当前边界

当前仓库只完成策划资料整理，不要在本阶段生成游戏代码、选择框架或安装依赖。任何实现工作都应从 MVP v0.1 开始，并先确认目标运行平台与技术栈。

## 2. 实现顺序

按以下顺序推进：

1. 先实现可测试的纯规则层：能源结算、资源变化、事件和升级效果。
2. 再实现最小 UI：状态展示、按钮、事件提示、升级弹层和结束画面。
3. 再接入输入、动画、音效和移动端适配。
4. 每完成一个系统，先运行测试并进行一局可玩的验证，再继续扩展。

## 3. 架构原则

- 将 Game Loop、规则计算、随机数、事件、升级和 UI 分开。
- 规则层不能依赖具体 UI 框架，方便单元测试和调数值。
- 所有关键数值集中配置，不要散落在组件或事件代码中。
- Tick 结算应尽量确定性：相同初始状态、随机种子和操作序列应得到相同结果。
- 随机事件和升级抽取支持固定种子，便于复现问题。
- UI 只展示状态并发出意图，不直接修改底层资源。

## 4. 开发约束

- 先完成 MVP_V0.1.md 中的“必须包含”，再考虑扩展。
- 不未经确认加入账号、联网、排行榜、付费、复杂存档或多人功能。
- 不用复杂真实电网模型替代易懂的游戏规则。
- 不通过隐藏随机数制造无解局面。
- 新增系统必须说明它服务于哪个核心决策，以及如何验证它带来的乐趣。

## 5. 测试要求

至少覆盖：

- Solar 产能、Home 消耗、Battery 充放电和 Grid 交易的基础结算。
- EV 充电与 Home 供电冲突时的优先级。
- Money、Family、Score 的边界值和 Game Over。
- 事件的触发、持续、结束和玩家应对结果。
- 升级效果确实改变状态或结算结果。
- 固定随机种子可以复现同一局关键结果。
- 暂停、重开、胜利和 Game Over 不会重复结算 Tick。

## 6. 验证方式

每次实现后至少完成：

- 自动化测试。
- 一局完整流程试玩。
- 一次异常或边界状态检查。
- 检查移动端窄屏布局和点击区域。

报告结果时要明确区分：已实现、已验证、暂未实现和需要产品决策的内容。

## 7. 代码风格与协作

- 使用清晰、领域化的命名：solarOutput、homeLoad、batteryLevel、family、money 等。
- 小步提交，每个提交只解决一个可描述的问题。
- 修改前先阅读现有文件和测试，不覆盖用户已有改动。
- 遇到需求矛盾时，以 MVP_V0.1.md 的范围和“可理解、可复盘、可重玩”原则为优先，并记录需要确认的决策。
- 不把未验证的数值平衡写成最终结论；将其视为可调参数。

## 8. 完成定义

一个阶段只有在以下条件都满足时才算完成：

- 需求范围内的功能已实现。
- 关键规则有自动化测试。
- 可完整开始、游玩、胜利或 Game Over、重开。
- 试玩者能说出自己为什么成功或失败。
- 没有为后续阶段提前引入未验证的复杂系统。
